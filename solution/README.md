# Capibara / Olist

PostgreSQL 16, SQL-модель и локальный Python API. CSV → `raw` (исходные text-поля) → `core` (типы, PK/FK, сущности) → `mart` (показатели) → пять SQL-ответов / API. Все статусы и исходные факты сохраняются. Заказ и доставка разделены 1:1; это снимок, не отдельные отправления.

## Запуск

Нужны Docker Compose и Python 3.13. Из папки `solution`:

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -r api/requirements.txt
bash scripts/setup.sh
bash bin/build.sh
bash bin/export_answers.sh
python3 api/setup_access.py
bash api/run.sh
```

`setup.sh` — только первичная загрузка: скачивает CSV в `data/`, поднимает PostgreSQL и загружает raw. При уже загруженном raw начинайте с `build.sh`. Не используйте `--reset`: он удаляет том solution. Ежедневная сборка не меняет raw; выполняется одной транзакцией и откатывается при ошибке.

DBeaver: localhost:**5433**, marketplace, учебные user/password `hack/hack`. Соседний проект на 5432 не используется. API: http://127.0.0.1:8004/docs. API-пароль генерируется в локальный `api/.env`, в Git не попадает. Пользователь API имеет SELECT только на разрешённых mart, без доступа к raw и записи в core. Не копируйте placeholder из `.env.example` как рабочий пароль.

GET `/api/overview`, `/api/sales/monthly`, `/api/sellers?limit=10&offset=0`, `/api/categories`, `/api/customers/repeat`. Ответ `{"data": [...], "meta": {...}}`. Счётчики — числа; суммы, средние, рейтинги и проценты — точные десятичные строки; отсутствующее — null; даты — ISO. Проценты уже в шкале 0–100. CORS: localhost/127.0.0.1:5173 и :3000; иной origin через API_CORS_ORIGINS. Это локальный API без HTTP-аутентификации, не публичный продакшен. Фронтенд — `solution/frontend`, запуск в его README.

## Что понимать на защите

- `model/00_migrate.sql`: явный переход старой схемы к отдельной доставке, без CASCADE.
- `model/01_schema.sql`: таблицы, типы, первичные и внешние ключи.
- `model/02_load_core.sql`: загрузка, сохранение исходников, отдельные нормализованные города/индексы, UNKNOWN для отсутствующей категории.
- `model/03_*.sql`: отдельный файл для каждой витрины. Позиции, платежи и отзывы агрегируются до JOIN, иначе суммы размножатся. Пропуск платежа не равен нулю.
- `queries/01…05`: пять коротких ответов. Продажи продавцов независимы от дополнительного рейтинга.
- `model/verify/`: проверки сохранности и синтетический тест рейтинга. Входные EDA-проверки `checks/` сохранены локально как промежуточный анализ, не публикуются и не заменяют тесты модели.
- `api/app.py`: маршруты; `api/database.py`: read-only запрос и точный JSON; `api/seller_query.sql`: присоединение рейтинга только для дашборда; `api/setup_access.py`: права и локальный секрет.

## Пять алгоритмов и контроль

1. Месяцы: сгруппировать delivered-заказы по месяцу оформления, суммировать цены товаров **без доставки**, добавить календарь пустых месяцев. 24 строки, один нулевой месяц, **13221498.11 BRL**.
2. Продавцы: взять только собственные позиции продавца из delivered-заказов; сложить price, отдельно посчитать уникальные заказы и позиции. Первый: **226987.93**.
3. Средний чек: сначала сложить price + freight на заказ, затем усреднить delivered-заказы: **159.88**. Строки и единицы считаются COUNT позиций; одна исходная позиция принята за одну единицу, отдельного quantity нет.
4. Повторность: соединить **orders с customer_context**, сгруппировать реальные заказы по customer_unique_id, отметить людей с >1 заказом. Все статусы: **96096 / 2997 / 3.12%**. Это не показатель повторных успешных покупок.
5. Категории: сложить delivered-цены по категориям, включая UNKNOWN; разделить на общую сумму. **74**, максимум **1233131.72**, общий итог **13221498.11**. Отсутствие перевода не теряет товар.

Оборот товаров без доставки и средний чек с доставкой — разные определения, не противоречие. Платежи не подгоняются под стоимость заказа. Средние, проценты и уникальные заказы по продавцам/категориям нельзя складывать.

## Дополнительный рейтинг

Название: **«Оценка однопродавцовых заказов»**. Все статусы. Подходят только заказы с COUNT(DISTINCT seller_id)=1. Сначала среднее отзывов заказа, затем среднее этих оценок по продавцу: каждый оценённый заказ имеет вес 1. Без оценок рейтинг NULL. Показываются число подходящих/оценённых заказов, покрытие и исключённые многопродавцовые заказы. Это принятое командой правило: отобранная выборка, оценка может включать доставку и не доказывает личную ответственность продавца.

## Проверки и условия кейса

```bash
python3 bin/verify_rebuild.py
python3 bin/verify_clean.py
python3 -m api.verify
```

Первое проверяет повторную сборку и сохранность raw/core/mart; второе собирает пустой core в отдельной временной БД и сравнивает все ответы; третье отдельно проверяет работающий HTTP API против mart и ограниченные права. Результаты и локальные пояснения остаются на диске в results/ и docs/, не публикуются. Ошибки источника отмечаются, не удаляются автоматически; карантин и история изменений пока не реализованы.

Условия организатора: модель из raw, ответы из core/mart, объяснимые ключи/качество, записка о решениях до половины страницы, концепция дашборда с формулами и стратегией развития. Этот репозиторий содержит техническую часть; дополнительные вопросы/вброс, итоговая записка, стратегия и подключение фронтенда не объявляются выполненными самим наличием SQL/API.
